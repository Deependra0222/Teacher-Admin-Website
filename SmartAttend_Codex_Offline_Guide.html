What the supplied 11-page technical project guide specifies

  • One classroom, Android-only student app, three ESP32 BLE beacons, Firebase, and teacher/admin web dashboard.
  • Student app screens: Login/Registration, Home/Current Class, My Attendance, History, Profile.
  • Data: students, subjects, timetable, sessions, attendance, devices, audit logs.
  • Future BLE rule: multi-node RSSI measurements, stability/dwell time and exit timeout; classroom thresholds require real calibration.
  • Example attendance policy: at least 75% Present, 50–74% Review, below 50% Absent; late arrival is a separate flag.

This handbook adapts that source design to an app-first, hardware-free 14-day build. Added engineering recommendations (Git, source abstraction, security, tests) are implementation guidance rather than statements from the original guide.

Build scope and architecture

Phase 1: no hardware

Student UI → Firebase login + timetable → SimulatedPresenceSource → attendance calculation → teacher dashboard.

Keep the source interface separate so BlePresenceSource can be added later. A teacher-controlled process should finalize official records; never trust arbitrary student-client writes as conclusive proof.

What you must NOT attempt during these 14 days

No face recognition, AI prediction, exact indoor positioning, iOS, multiple classrooms, Play Store release, or real BLE scanning without hardware. Avoid unsupported claims of anti-proxy accuracy.

Part A — Start from zero on Windows

Do these steps before asking Codex to make large code changes.

1. Install Android Studio

Download from https://developer.android.com/studio, run the Windows installer, accept recommended SDK components, and wait for installation. A reasonably modern Windows laptop with enough disk space is needed.

Verify: Android Studio opens to its welcome screen.

2. Create an Android project

Choose New Project > Empty Activity (Kotlin + Compose template). Name: SmartAttend. Package: com.smartattend.app. Minimum SDK: API 26. Save in C:\Projects\SmartAttend (or a folder you can find). Finish and wait for Gradle sync.

Verify: MainActivity.kt and app/build.gradle.kts are present.

3. Run the untouched starter app

Connect an Android phone with USB debugging enabled; accept its debugging prompt. Or create an emulator in Android Studio Device Manager. Select device and press Run (green triangle).

Verify: The starter screen opens on the phone/emulator.

4. Open the SAME folder in Codex

Desktop app: open/select the SmartAttend project folder. VS Code extension: File > Open Folder, choose SmartAttend, then open Codex. Codex web: connect a GitHub repository first; local instructions differ. Do not create a second unrelated project.

Verify: Codex can inspect MainActivity.kt in the same folder Android Studio uses.

5. Run Prompt P0

Copy and paste P0 below into Codex. Permit only changes you understand. Ask Codex to tell you exactly what changed and whether Gradle actually built.

Verify: AGENTS.md, PROJECT_STATUS.md, PROJECT_PLAN.md exist and build result is known.

6. Save your first Git checkpoint

In the project folder, initialize Git if needed and commit a first working state. Inspect .gitignore, especially local.properties, signing files, service credentials. Keep a second backup outside the laptop if possible.

Verify: You can recover the working starter project even if later code fails.
Codex interface matters. Desktop app or editor extension can usually work with the local folder directly. Codex web typically uses a connected repository. The key rule: Codex and Android Studio must refer to the SAME project, not separate copies.

Windows build and checkpoint commands

Open the terminal in the SmartAttend project root (where gradlew.bat exists):

.\gradlew.bat assembleDebug

After a successful debug build, the APK is usually at app\build\outputs\apk\debug\app-debug.apk. For version control, install Git and then use:

git init
git status
git add .
git commit -m "SmartAttend starter project"

Check .gitignore before adding files. Never commit passwords, private signing keys or service-account private keys. If Git asks for your identity, configure your name and email first.

P6 Simulated attendance engine Days 9–10
Paste into Codex with your project open
Implement a clearly labeled SIMULATION ONLY attendance engine in the existing SmartAttend Android app. I do not own any ESP32 boards yet.

ARCHITECTURE
- PresenceSource abstraction that emits presence state/events.
- SimulatedPresenceSource with manual Enter Classroom and Exit Classroom buttons.
- Keep a future BlePresenceSource placeholder/integration note separate; no fake BLE readings.
- AttendanceCalculator and a testable clock abstraction.

LOGIC
1. Require a signed-in student who is enrolled in an active subject/batch/session.
2. On demo Enter, record event and start accumulating duration.
3. On demo Exit, close the current interval.
4. Re-entry continues accumulating time without duplicate counting.
5. At session end, close any open interval and compute percentage = confirmed minutes / scheduled or configured lecture minutes * 100.
6. Example policy: >=75% Present, 50% to <75% Review, <50% Absent. Track Late separately using a configurable grace period.
7. Reject inactive/wrong-batch/duplicate events.
8. Use a controllable fake clock for fast testing without waiting an hour.
9. Label ALL simulated records and screens DEMO / NOT VERIFIED BY BLE.
10. Separate untrusted student-reported presence evidence from teacher-authorized final records.

TESTS
100%, 75%, 74.9%, 50%, 49.9%, re-entry, repeat enter/exit, late arrival, early exit, wrong enrollment, inactive session, session end with open interval.

Do not claim proxy prevention or secure physical presence. Run real tests/build where possible; update PROJECT_STATUS.md and stop.

Part D — Firebase manual checklist

These steps are performed in your own Firebase Console. Codex can write code, but it cannot invent your cloud configuration.

  1. Open console.firebase.google.com and create a Firebase project named SmartAttend.
  2. Add an Android app with com.smartattend.app (must exactly match your app ID).
  3. Download google-services.json and put it inside SmartAttend/app/.
  4. Enable Email/Password in Authentication → Sign-in method.
  5. In Cloud Firestore, create the database in a suitable region. Deploy restrictive security rules; do not leave a public test database.
  6. Create at least two student test accounts and one teacher test account. Teacher permissions must be assigned by a trusted admin, never through an ordinary student registration form.
  7. Use the Firebase Android setup guide to check compatible plugins and SDK modules. Do not put a service-account JSON key in the Android or web app.
  8. Use P3 and P4 for integration, test separate identities, and verify that students cannot edit finalized records.
Security limitation: BLE presence data sent by a student's phone is untrusted client input. This demo should never be represented as tamper-proof official attendance. Classroom policy and backend validation are required for a real deployment.

Part F — Troubleshooting and recovery

For any coding issue, give Codex the full error and paste P10. Do not ask it to rewrite everything.

Codex says it cannot find project files

It is likely working in the wrong folder. In Android Studio use File > Open to locate the project; then open that exact directory in Codex. Check that settings.gradle.kts is visible.

Gradle sync or build fails

Copy the full first error, including lines above it, and use Prompt P10. Check internet connectivity for downloading dependencies, installed SDK, JDK configuration and Gradle compatibility. Do not blindly replace version numbers.

App does not appear on phone

Enable Developer Options and USB Debugging, confirm phone authorizes this PC, try a data-capable USB cable, select the actual device and hit Run. Alternatively use an emulator.

The app looks good but nothing changes

Check whether you are using demo/mock data. Verify buttons have real callbacks, view models observe state, and there is no hardcoded UI-only fake logic.

Firebase login fails

Check email/password provider enabled, the user exists, network is working, google-services.json matches your package/project, and the full Firebase error code. Never share passwords in prompts.

Firestore permission denied

Likely security rules or document UID mismatch. Do not change rules to allow read/write for everyone; inspect Auth UID, document paths and intended roles.

Teacher has no access

Check the teacher account has been granted a trusted role by an administrator; never add a client-side “make me teacher” button.

Simulated attendance duplicates minutes

Check overlapping intervals, repeated Enter events and session-end closure. Use test clock and unit tests; run Prompt P6/P10.

App lost after browser tab closed

Local files remain in your project folder, and this guide stays available offline. Open the same folder, then paste P11 into a new Codex chat.

Need to pause a project for a day

Ask Codex to update PROJECT_STATUS.md and commit or back up files. Export progress/notes from the HTML handbook as a separate .json backup.

Part H — Connecting ESP32 later

This is Phase 2 after the app-only demo is working and you obtain three compatible BLE ESP32 boards.

  1. Program and verify one ESP32 BLE advertiser using Arduino IDE.
  2. Use an Android BLE scanner to confirm the identifier and RSSI.
  3. Implement BlePresenceSource for Android with the correct permissions.
  4. Add the remaining two beacons and record separate node RSSI values.
  5. Use filtering and initial two-of-three stable presence logic with dwell/exit timeout; calibrate at front/back seats, door, corridor and behind walls.
  6. Record measured false-positive and false-negative rates; do not claim exact indoor triangulation.
  7. Test background behavior on your phone with battery optimization and Android foreground-service limitations in mind.
  8. Maintain teacher corrections and document proxy-phone, spoofing and client-trust limitations.

When the hardware arrives, use prompt P12. The source guide gives illustrative 10–15-second confirmation windows and example RSSI values, but they are not universal thresholds.
